# core.result.py 设计文档

### 设计原因

项目内存在大量基础设施模块，由于存在层次关系，需要向上游返回失败时的详细信息。

如果完全依赖 `throw` 抛异常，会有以下问题：

- 频繁定义和传递大量 `Exception`
- 调用方容易遗漏错误分支，导致异常未被处理，而直接击穿到更高层
- 一些并不适合抛异常的情况难以表达，如“日志被级别过滤，因此没有实际写入”

因此选择引入一个轻量的 `Result[T]`，把“成功 / 失败”作为返回值接口的一部分，显式表达出来。

### 设计目标

`Result[T]` 当前承担的职责有三类：

- 用 `ok` 明确区分当前操作是否成功
- 在失败时通过 `error`、`code` 和 `data` 传递足够的报错信息
- 允许附带额外上下文
- 不强迫调用方立刻抛异常，允许调用方进行多方式处理

这套设计的重点是让底层模块统一使用一种足够简洁且明确的错误传播方式。

### 字段语义

- `ok`: 当前结果是否成功
- `value`: 成功时返回的值；在少数场景下，失败结果也允许带一个值
- `error`: 失败时的主错误信息
- `code`: 失败类别的稳定标识，便于上游做程序化分支
- `data`: 附加上下文字段，用于携带路径、异常文本、索引、重试信息等细节

其中 `error` 为可读报错信息，而 `error` 则用于判断失败分支。

这样上游既能直接打印可读信息，也能在不依赖错误文案的前提下判断失败类型。

### 为什么失败结果也允许携带 value

存在操作失败，但失败前已经构造出部分有意义对象的场景。

例如日志模块在重试耗尽时，会把原本准备写入的 `LogRecord` 一并放回失败结果中，便于上游决定是否补打、重试或上报。

故 `value` 不等于成功，`ok` 才是成功与否的唯一判据，调用方不能因为拿到了 `value` 就把结果当作成功。

### 为什么成功结果允许没有 value

部分操作只关心是否成功，如文件写入、日志写入、目录创建。

因此 `Result.success()` 允许不传 `value`，用来表达“成功但没有需要消费的结果值”。

然而，此时虽然 `Result.success()` 可以合法存在，但不能被 `unwrap()` 或 `expect()` 当成普通值读取。

### `unwrap()` / `expect()` 的边界

项目整体倾向于用 `Result` 替代异常传播，但并不意味着完全不抛异常。

`unwrap()` 和 `expect()` 属于显式的断言式接口：

- 当 `ok=False` 时会抛出 `RuntimeError`
- 当 `ok=True` 但 `value is None` 时也会抛出 `RuntimeError`

也就是说，当前实现中：

- `Result[None]` 适合用 `ok` 判断，不适合直接 `unwrap()`
- `unwrap()` 适合在调用方确定“必须成功且必须有值”时调用
- `expect(message)` 和 `unwrap()` 的区别主要在于前者会把 `message` 补进异常信息里

简而言之，其目的在于把断言写得更直接。

### 当前项目内的推荐使用方式

推荐在以下场景使用 `Result`：

- 低层模块对外暴露可能失败的接口
- 中层模块优先透传或重包装失败结果
- 只有在非常明确的断言点上才调用 `unwrap()` 或 `expect()`

以下场景应避免直接 `unwrap()`：

- `Result.success()` 可能不带值
- 失败但可能附带部分 value

### 与日志模块的关系

`Result` 当前最能体现设计价值的地方之一，是日志模块的“退化成功”语义。

例如文本日志追加失败时，日志模块会尝试根据结构化日志重建文本视图。若重建成功，最终仍返回成功结果，但会在 `data` 中附带：

- `log_rebuilt=True`
- 原始文本追加失败的错误信息

若结构化日志已落盘，但文本视图重建也失败，则仍可能返回一种“主数据保住了，但视图退化”的成功结果，并通过 `data` 标记：

- `log_view_degraded=True`

这种语义若只靠异常很难表达清楚，但用 `Result.success(..., **data)` 可以自然承载。

### 当前设计的取舍

`Result[T]` 目前是一个非常轻量的封装，并没有继续强行扩展出以下内容：

- map / and_then 一类链式函数式接口
- 强约束的错误枚举体系
- 自动堆栈包装或统一异常桥接层

对当前项目阶段而言，`Result` 有如下目标：

- 降低低层模块的错误传播成本
- 让错误返回格式统一
- 让测试可以直接断言失败语义
- 保持足够低的理解门槛

后续高层模块开发时将尽可能保持 `Result` 的纯净性，避免过度添加功能。
