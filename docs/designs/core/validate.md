# core.validate.py 设计文档

### 设计原因

由于配置类涉及到可持久化，出现了大量 `from_dict(data)` 这样的反序列化入口。

最初实现是在函数流程里手动写校验：

- 先手动判断 `data` 是否为 `dict`
- 再逐个 `data.get(...)` 补默认值
- 通过 `cast(...)` 告知类型检查器当前字段应该是什么类型
- 在局部位置再判断 `kind`、`slice_config` 等特殊字段

随着配置与状态数据类增多，这种方式暴露出了几个问题：

- 样板代码重复，阅读成本高
- `cast(...)` 只对静态类型检查器生效，并不提供运行时校验
- 数据异常无法在入口函数探查，而是在执行阶段才暴露
- 默认值、非空约束、列表元素类型约束等逻辑散落在不同函数体中，后续维护容易不一致

为解决这类问题，core.validate 中实现了一个字典字段校验器，对任何数据类的字典类型校验都可生效，作为最底层依赖放在 core 层。

选择装饰器的形式实现校验时，字段约束可以集中写在函数定义附近，理解成本更低。

### 设计理念与边界

这一校验器只做最基础的常见校验：

- 字段是否存在
- 字段是否允许为 `None`
- 字段类型是否正确
- 字段缺失时是否补默认值
- 字段是否必须非空
- 字段值是否属于某个字面量集合
- 列表或元组中的元素类型是否正确
- 在通过基础校验后，对字段值做一次局部转换
- 在必要时执行简单的自定义校验函数

### `FieldRule` 的设计目的

`FieldRule` 是单字段规则的描述对象。它的存在目的是把原本分散在 `from_dict()` 函数体里的隐含规则显式化。

其每一项配置都有明确用途：

- `type_`: 字段类型
- `required`: 字段是否必填
- `allow_none`: 是否允许为 `None`
- `default`: 字段缺失时的默认值
- `literal`: 用于枚举字符串取值字段
- `item_type`: 用于容器字段
- `non_empty`: 是否禁止字符串为空串
- `validator`: 用于承接未来更细粒度但仍较简单的语义校验
- `transform`: 基础的变换逻辑

其中，`transform` 的引入非常关键。例如 checkpoint 中的 `input_files` 在持久化时更适合保存为 `list[str]`，但恢复到内存对象后，配置模型实际使用的是 `tuple[str, ...]`。若没有 `transform`，这种“外部表示”和“内部表示”的转换就只能继续散落在各个 `from_dict()` 里。

通过 `transform`，可以明确表达先验证输入是不是 `list[str]`，再把它转换成内部使用的 `tuple[str, ...]`

### `validate_dict_fields` 的实现思路

`validate_dict_fields(...)` 本质上是一个针对 `from_dict(data)` 场景的 decorator。

其执行流程如下：

1. 根据函数签名定位原始 `data` 参数
2. 检查传入对象是否为 `dict`
3. 按字段规则依次校验每个声明字段
4. 对缺失字段补默认值
5. 对通过校验的字段执行规范化
6. 生成一份新的、已经过校验与整理的字典
7. 将这份字典重新传给原函数

处理后会把规范化的结果传回原函数，进一步减少冗余逻辑，使下游 `from_dict()` 拿到的是已经过初步清洗的数据。

### 为什么默认保留未知字段

实现中默认 `keep_unknown=True`，即未在规则中声明的字段仍会保留在传入字典中。

原因在于当前项目的 `from_dict()` 往往并不只是“平铺字段 -> dataclass”这么简单，它还会承担：

- 根据 `kind` 做任务配置分发
- 读取嵌套字典并进一步构造子对象
- 在部分场景下保留额外元数据供后续逻辑消费

如果在第一层校验器里默认把未知字段全部过滤掉，会让 decorator 侵入业务分支逻辑，导致它从“边界校验”逐渐演变成“对象装配器”，这不符合当前设计目标。

所以现阶段的原则是：

- decorator 负责声明过的字段
- 未声明字段是否使用，由函数体自行决定

### 为什么单独处理 bool

实现中对 `bool` 做了一次特殊处理，即当规则期望 `int` 或 `float` 时，不接受 `True` / `False`。

这是因为 Python 的类型体系中，`bool` 是 `int` 的子类，`isinstance(True, int)` 会返回 `True`。若不额外处理，会导致一些本应被拒绝的脏配置被误判为合法。

这个规则虽然看起来细小，但对于配置与 checkpoint 解析来说是必要的。否则“布尔值误入数值字段”这种错误很容易静默通过。

### 与 conf 模块的关系

当前这套能力主要被用于 `conf.task` 与 `conf.state` 的 `from_dict()` 入口。

在 `BaseTaskConfig.from_dict()` 中，它承担两层作用：

- 先在公共入口统一校验共享字段
- 再在分支构造函数中校验各任务类型专属字段

这样做的理由是，任务配置天然是一个带 `kind` 的判别联合。若把所有字段规则完全塞在一层里，可读性会迅速下降；而拆成“公共规则 + 分支规则”之后，结构会更清晰，也更便于后续扩展新任务类型。

在 `SliceState.from_dict()` 与 `TaskState.from_dict()` 中，它的作用则更偏向“阻止明显脏数据进入运行时状态对象”，例如：

- 把 `completed_slices=["0"]` 这种错误尽早拦下
- 把 `slice_states` 中元素不是字典的情况提前暴露
- 把非法 `status` 或 `current_stage` 拦在恢复入口

这样可以减少“恢复成功但执行中途才爆炸”的问题。
